# 模型翻译交接文档（2026-04-26）

## 1. 结论

当前项目内的规则式数理化翻译链路（`scientificTranslation` 及其衍生补丁）不再作为主路线，标记为**待拆除**。  
后续主方案改为：**按用户设置开关控制是否启用模型翻译**。

## 2. 本轮验证结果

### 2.1 已验证有效的方法

在独立 demo 中已验证以下方法有效，并优于规则链稳定性：

1. 云端模型实时翻译（阿里云百炼 `Qwen3.5-Flash`）。
2. 分片段翻译（仅翻译光标附近片段，而不是整段重写）。
3. 请求防抖 + 可取消并发请求（只保留最新请求）。
4. 前端缓存（相同输入片段命中缓存，显著减少重复请求）。
5. 输出双轨：
   - `rendered_latex` 用于渲染；
   - `translated_text` 用于可读文本和回写候选。
6. 置信度阈值控制（高置信度自动提交，低置信度保留影子结果人工确认）。

### 2.2 实测特征（基于 demo 日志）

1. 单次请求端到端耗时主要集中在 `~0.75s - 1.15s`。
2. 单次总 token 约 `~235 - 264`。
3. 对自然语言输入（如“e的x次方 + a + x”）输出稳定性明显高于规则映射。
4. 延迟不可避免，工程目标应从“消灭延迟”改为“降低体感阻塞”。

## 3. 现有规则链状态

### 3.1 状态定义

规则式翻译链定义为：

1. `frontend/src/lib/scientificTranslation.ts`
2. `frontend/src/lib/scientific/` 下 parser/classifier/tokenizer/pipeline
3. `MathContentEditor` 中依赖规则归一化的实时回写逻辑

以上链路统一标记为：

- `Deprecated`（保留过渡期兼容）
- `Pending Removal`（进入拆除待办）

### 3.2 风险说明

1. 规则链在连续输入、IME、回删、复合表达上存在结构性脆弱，不适合作为最终主链。
2. 继续补规则会导致回归成本持续上升，且无法覆盖自然语言开放表达。

## 4. 新方案（主线）

## 4.1 开关策略

在设置页增加用户级开关（持久化）：

- `启用模型翻译（实验）`

开关行为：

1. `OFF`：保持纯文本/低风险规则（仅最小确定性处理）。
2. `ON`：启用模型分片翻译链（防抖、缓存、置信度阈值、可取消请求）。

默认值建议：

1. Agent 输入框：默认 `OFF`（降低误触风险）。
2. 题卡富文本作答：可灰度默认 `ON`（需带“实验”标识）。

## 4.2 运行模式

模型翻译链不直接接管整段输入，采用：

1. 源文本主缓冲（稳定输入不被阻断）。
2. 片段级异步翻译（光标附近片段）。
3. 影子结果渲染。
4. 高置信度自动提交 + 低置信度手动确认。

## 4.3 最小接口契约

模型返回固定结构：

```json
{
  "translated_text": "y = e^x + a + x",
  "rendered_latex": "y = e^{x} + a + x",
  "confidence": 0.95,
  "notes": "..."
}
```

## 5. 执行计划

1. 设置页新增开关项 + 本地持久化。
2. 输入组件接入开关状态分流（规则链/模型链）。
3. 先在 agent 输入框灰度上线模型链。
4. 稳定后扩展到题卡富文本作答区。
5. 规则链进入冻结：不再新增规则，只允许修阻断性 bug。
6. 迁移完成后拆除 `scientificTranslation` 主链及相关补丁。

## 6. 验收标准

1. 开关 `ON/OFF` 行为清晰，跨重启状态恢复正确。
2. `ON` 时：
   - 连续输入不出现整段清空或光标跳跃；
   - 请求可取消且不会旧响应覆盖新输入；
   - 有 token/延迟日志可追踪。
3. `OFF` 时：
   - 不触发模型调用；
   - 保持纯文本输入稳定。
4. 线上灰度指标：
   - 平均响应延迟；
   - 单次输入请求数；
   - token 消耗；
   - 用户回退率/关闭开关率。
