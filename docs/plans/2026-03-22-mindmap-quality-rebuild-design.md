# 脑图质量重构设计

## 1. 背景

当前脑图生成为单轮直出：

- `exam_document` 场景下，后端先将题目或文本块压缩为少量字符串，再调用一次模型直接生成整棵脑图。
- `uploaded_file` 场景下，后端将原文件上传到百炼，再调用一次模型直接生成整棵脑图。
- 如果 LLM 失败，则回退到 `page/snippet` 风格的系统树。

这个实现能生成“可显示的脑图”，但不能稳定生成“高质量脑图”。主要问题如下：

- 输入被预裁剪，模型拿不到完整信息，容易生成局部化主题。
- 单轮 prompt 直接出树，任务过重，输出结构不稳定。
- 单文档和多文档共用一套弱约束 prompt，无法针对不同规模稳定控制粒度。
- fallback 结构本质是索引树，不是思维导图，会污染最终质量。
- 当前没有生成后质量闸门，低质量结果会直接落库。

本次重构目标不是知识图谱，而是高质量思维导图。

## 2. 目标

### 2.1 用户目标

用户在生成脑图时可以显式选择两种模式：

- `知识结构图`：强调概念体系、原理层级、模块归属、结构关系。
- `复习/考试导图`：强调考点、题型、方法、易错点、综合模型。

### 2.2 系统目标

- 支持单文档生成。
- 支持 1 到 50 个文档合成同一张总脑图。
- 默认优先使用原文件直传百炼，而不是本地抽文本作为主路径。
- 使用同一个服务内流水线实现，不拆独立 agent。
- 提升质量时不依赖额外版面模型、关键词规则、正则规则。
- 百炼远端文件仅作临时推理输入，不作为长期存储。

### 2.3 非目标

- 不将当前系统升级为知识图谱或 ontology 平台。
- 不在本阶段引入额外 OCR/版面识别模型。
- 不为试卷做硬编码特化规则。

## 3. 约束

### 3.1 模型与平台约束

已知千问模型限流与上下文约束如下：

- 最大输入长度：`10M`
- 上下文长度：`10M`
- 最大输出长度：`8K`
- `RPM = 1200`
- `TPM = 60000`

这些约束直接影响多文档并发策略、任务批次规模、输出树的节点预算。

### 3.2 存储约束

- 百炼账号远端文件数量存在硬上限。
- 用户原始文档长期保存在本系统服务器。
- 百炼文件仅作为临时推理输入，任务完成后应尽快删除。

## 4. 核心设计

### 4.1 总体思路

将当前“单轮直出脑图”重构为“多阶段、单服务内流水线”：

1. `Doc Outline`：每个文档先生成文档级提纲，而不是直接生成最终脑图。
2. `Global Merge`：多文档时，将多个文档提纲合并为全局提纲。
3. `Mindmap Expand`：根据用户选择的模式，将提纲展开为最终脑图树。
4. `Quality Gate`：对结果评分，不达标则定向重试后续阶段。

这不是多 agent 设计，而是后端服务内部的阶段化生成流水线。

### 4.2 为什么优先原文件直传

在当前项目条件下，原文件直传应作为主路径，原因如下：

- 本地目前没有高质量文档解析能力，只有 Python 抽文本，信息损失会直接损伤脑图质量。
- 1 到 50 文档场景下，本地先解析再拼装大文本，并不比直传原文件更轻。
- 原文件直传后，可以把文档理解责任交给百炼模型，避免本地解析成为质量上限。

因此主路径为：

- `single document -> upload original file -> Doc Outline`
- `multiple documents -> per-document upload -> per-document Doc Outline -> merge -> final map`

文本直传仅作为降级路径：

- 文件上传失败
- 百炼文件能力异常
- 文件类型不受支持

### 4.3 双模式脑图

生成请求新增 `mindmap_mode` 字段：

- `knowledge_structure`
- `exam_review`

该字段贯穿：

- 前端模式选择 UI
- 后端请求 schema
- 提纲 prompt
- 展开 prompt
- 质量评分规则
- 缓存 key

不同模式下的目标结构：

#### 知识结构图

- 一级节点：模块/领域/主干概念
- 二级节点：关键原理、核心机制、子模块
- 三级节点：细分概念、条件、典型联系

输出要求：

- 同层粒度一致
- 避免题目化标题
- 减少情境化用语

#### 复习/考试导图

- 一级节点：核心考查模块
- 二级节点：高频考点、题型、模型
- 三级节点：方法、易错点、关键变式

输出要求：

- 强调考查导向
- 保留复习价值和解题价值
- 避免退化成知识点罗列

## 5. 生成流水线设计

### 5.1 阶段 A：Doc Outline

每个文档单独生成文档级提纲，输出统一 JSON，示意结构如下：

```json
{
  "title": "文档标题",
  "mode": "knowledge_structure",
  "document_summary": "该文档的高层摘要",
  "topics": [
    {
      "topic": "一级主题",
      "summary": "主题摘要",
      "subtopics": [
        {
          "topic": "二级主题",
          "summary": "二级摘要",
          "evidence_hints": ["页码/题号/片段线索"]
        }
      ]
    }
  ]
}
```

约束：

- 不直接输出最终 MindMapDocument。
- 不包含数据库字段、节点 id、questionRefs。
- 每个文档先得到一个稳定、紧凑、可合并的中间结果。

### 5.2 阶段 B：Global Merge

当文档数大于 1 时执行：

- 输入：多个 `Doc Outline`
- 输出：一个 `Global Outline`

职责：

- 合并同义主题
- 去除明显重复主题
- 统一同层粒度
- 形成全局主干结构
- 标注主题来源分布，便于覆盖率统计

多文档场景不再把 50 份原文件同时塞进一次请求，而是只合并中间结果。

### 5.3 阶段 C：Mindmap Expand

输入：

- 单文档：`Doc Outline`
- 多文档：`Global Outline`

输出：

- 最终 `MindMapDraft`
- 然后再转换成 `MindMapDocument`

该阶段只负责：

- 确定最终层级
- 生成节点标题和摘要
- 控制脑图宽度与深度

不负责：

- 再次理解全文
- 重新做跨文档融合

### 5.4 阶段 D：Quality Gate

生成后先评分，再决定是否落库。

评分维度：

- `coverage_score`：是否覆盖全部文档或主要主题
- `duplication_score`：重复主题是否过多
- `depth_score`：是否过浅或过度扁平
- `granularity_score`：同层粒度是否一致
- `mode_alignment_score`：是否符合用户选择的模式

触发重试规则：

- 第一阶段失败：只重试当前文档的 `Doc Outline`
- 第二阶段失败：只重试 `Global Merge`
- 质量评分不达标：只重试 `Mindmap Expand`

原则：

- 不做全链路盲目重跑
- 重试次数有限
- 所有重试原因必须写日志

## 6. 多文档性能与并发设计

### 6.1 并发原则

只有 `Doc Outline` 阶段可并发。

原因：

- 每个文档的提纲生成彼此独立
- 合并阶段与展开阶段是串行全局操作

### 6.2 并发池

后端增加脑图任务并发池，不允许无上限直接并发 50 个上传与生成任务。

初始建议：

- `outline_concurrency = 4`
- 根据实际 `RPM/TPM` 再调参

理由：

- `RPM 1200` 看起来足够高，但真实瓶颈常在 `TPM 60000`
- 文件直传场景中，请求本身耗时较长，盲目并发会导致峰值堆积
- 输出上限只有 `8K`，单次结果太大时仍会截断，需控制节点预算

### 6.3 Map-Reduce 合并

文档数较多时不应一次性合并全部 outline。

建议：

- 1 到 8 文档：直接合并
- 9 到 24 文档：按桶分组后两层合并
- 25 到 50 文档：三层 map-reduce 合并

这样可以：

- 降低单次 prompt 复杂度
- 降低合并结果失控风险
- 提高总图稳定性

### 6.4 节点预算

受 `8K` 输出限制，最终脑图必须做动态节点预算。

建议：

- 单文档：20 到 40 节点
- 2 到 10 文档：40 到 80 节点
- 11 到 50 文档：80 到 140 节点

超过预算时优先压缩：

- 叶子摘要长度
- 低重要性分支数量

不要压缩：

- 一级主干覆盖
- 模式关键节点

## 7. 百炼文件治理

### 7.1 主原则

百炼文件仅做临时推理输入，不作为存储层。

### 7.2 生命周期

主路径为：

1. 上传本地原文件到百炼
2. 完成 `Doc Outline` 生成
3. 立即调用远端删除
4. 本地仅记录 registry 状态与审计信息

### 7.3 删除可靠性

不能只做“调用 delete”，必须做：

- 成功后立即删
- 失败进入重试队列
- 定时扫尾清理
- 水位告警与限流

### 7.4 多文档场景

50 文档批量任务下的风险不是单次是否删除，而是峰值占用和失败残留。

因此需要：

- 上传并发池
- 删除重试任务
- 远端残留监控
- 超高水位限流

## 8. 数据结构改造

### 8.1 新增中间结构

后端新增中间 schema：

- `MindMapMode`
- `DocOutline`
- `DocOutlineTopic`
- `GlobalOutline`
- `QualityReport`

### 8.2 请求结构

生成请求新增：

- `mode`
- `source_ids` 或批量 source 描述

从而支持：

- 单文档生成
- 多文档生成一张总图

### 8.3 缓存键

缓存必须包含：

- `tenant_id`
- `workroom_id`
- `mode`
- `source set hash`
- `pipeline version`

否则切换模式或切换文档集合时会命中错误结果。

## 9. 前端改造

前端需要补齐以下能力：

1. 生成模式选择
2. 多文档参与范围展示
3. 长任务状态展示
4. 失败重试与阶段提示

建议 UI 结构：

- 模式切换：`知识结构图 / 复习导图`
- 生成按钮：显式触发，不自动生成
- 进度文案：
  - `上传文档中`
  - `分析单文档结构中`
  - `合并多文档结构中`
  - `生成脑图中`

## 10. 日志与可观测性

当前脑图功能排障仍然偏黑盒，本次重构必须补齐日志。

最少需要记录：

- 请求模式
- 文档数量
- 并发批次数
- outline 生成耗时
- merge 耗时
- expand 耗时
- 质量评分
- 是否重试
- 重试原因
- 百炼文件上传数、删除成功数、删除失败数

禁止仅记录“成功/失败”，必须记录阶段性上下文。

## 11. 回退策略

当前 `page/snippet` fallback 质量过差，不应再作为正常结果直接落库。

新回退策略应为：

- 若 `Doc Outline` 失败，则返回可重试错误
- 若必须回退，也应回退到“最小语义提纲”，而不是 `Page 1 / Snippet 1`

原则：

- 不让低质量索引树伪装成思维导图

## 12. 分阶段实施建议

### Phase 1

- 新增前端模式选择
- 后端请求打通 `mode`
- 单文档改为 `Doc Outline -> Mindmap Expand`

### Phase 2

- 多文档 outline 并发生成
- `Global Merge`
- map-reduce 合并

### Phase 3

- `Quality Gate`
- 定向重试
- 新 fallback 策略

### Phase 4

- 百炼文件即传即删
- 删除重试
- 水位限流
- 监控告警

## 13. 决策结论

本次脑图重构采用以下最终决策：

- 不做独立 agent
- 不做知识图谱
- 用户可选 `知识结构图 / 复习导图`
- 默认优先原文件直传百炼
- 单文档与多文档统一走多阶段流水线
- 多文档通过 `Doc Outline` 并发 + `Global Merge` 串行收敛
- 用 `Quality Gate` 代替当前一次直出的裸落库策略
- 百炼远端文件必须临时化，处理完成后删除
